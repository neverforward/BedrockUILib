# Contributing

## Environment

- Windows x64, xmake, clang-cl, C++20.
- LeviLamina client SDK 26.51.x is pinned in `xmake.lua`; the package is fetched
  from the `levimc-repo` xmake repository.
- `git config --global core.longpaths true` is required (long SDK header paths).

## Build

```bash
xmake f -y -p windows -a x64 -m release --target_type=client
xmake build BedrockUILib
```

Always configure before building. `xmake build -r` can silently reuse a debug
configuration; after every build check the artifact's `LastWriteTime`, size and
SHA-256 under `build/windows/x64/release/` instead of trusting the exit code.

`--target_type=server` fails at configure time. Do not add a server variant, a
server branch or a `src-server/` directory: the library is client-only by design.

## Test

```bash
xmake f -y -p windows -a x64 -m debug --tests=y --target_type=client
xmake build BedrockUILibTests
xmake run BedrockUILibTests
```

Then reconfigure back to release with `--tests=n` before building the mod:

```bash
xmake f -y -p windows -a x64 -m release --tests=n --target_type=client
xmake build BedrockUILib
```

Rules:

- `src/` is pure logic: no `mc/` and no `ll/` includes. Layout math, hit tests,
  focus order, text measurement (behind an interface), theme resolution, data
  binding and version macros must be testable there without a game.
- `src-client/` is engine glue. Anything that needs the game is verified manually
  in game, not by a unit test.
- Every public header is force-compiled by `src-test/common/include_all.cpp`,
  which the test target regenerates before each build. A header that stops
  compiling therefore fails the build even when no test includes it.

## Editor (clangd)

Language server data is generated by xmake into `compile_commands.json` at the
repository root (git-ignored). It **must match the configuration you build**:

```bash
# demo sources (src-demo/, BUL_DEMO) need --tests=y in the database too
xmake f -y -p windows -a x64 -m debug --tests=y --target_type=client
xmake project -k compile_commands
```

If clangd reports `'bul/demo/DemoPanel.h' file not found`, missing `_tr` literal
operators or `Call to deleted function 'make_unique'`, the database was generated
from a configuration without `--tests=y` (so it lacks `-DBUL_DEMO`,
`-Isrc-demo`). Regenerate it and restart the language server. `.vscode/settings.json`
already points clangd at `${workspaceFolder}` and disables the MS C++ IntelliSense
engine so the two do not report different sets of diagnostics.

## Warnings

`/W4` and the clang-cl warning set in `xmake.lua` must stay clean. Fix the code;
do not add a suppression for a new warning.

## Hooks

Any engine hook the library needs is installed by the library exactly once, at
enable time, and removed at disable time. Consumers never hook anything: the
public API only registers screens, panels and HUD elements. Two dependents that
both hook the same engine function is the failure mode this rule exists to
prevent.

## Commits and changelog

- Imperative subject, at most 72 characters, English; the body explains why.
- Do not commit generated artifacts (`bin/`, `build/`, `.cache/`).
- `README.md`, `README.zh.md`, `docs/*.md` and `CHANGELOG.md` change in the same
  commit as the code they describe.
- `CHANGELOG.md` uses `## [Unreleased]` with `### Added`, `### Changed`,
  `### Fixed`, `### Removed`, and one short line per change: state what was done,
  not why or how (the commit body and the docs carry the reasoning).
- Version is generated, never hand-edited: `src/bul/Version.h.in` is rendered by
  xmake into `build/generated/bul/Version.h` (first on the include path). The only
  input is the `BUL_VERSION` environment variable, which the release workflow
  exports from the git tag: `.github/workflows/release.yml` turns `v1.2.3` into
  `BUL_VERSION=1.2.3` and stamps the same value into the shipped `manifest.json`.
  Every other build renders `0.0.0` on purpose. The checked-in
  `src/bul/Version.h` is only a fallback for an unbuilt checkout.
